## 1. Overview

This TDD specifies the minimal design needed to satisfy [PRD REQ-000041](../prd/REQ-000041-req-000041.md): extract greeting logic in `hello.py` into a pure function `greet(name: str = "world") -> str`, preserve the existing CLI contract (`python hello.py` prints `hello world\n`), and add pytest unit tests in `test_hello.py` covering the default invocation, a custom name, and the existing CLI subprocess behavior.

**Proportionality note.** This is a tiny refactor of a single-file Python script. It introduces no new modules, no persisted state, no external integrations, no protocol surface, and no concurrency. Per the agent's "Scale Rigor to Task Complexity" guidance, several template sections are explicitly marked `N/A — no new surface`. The design surface is exactly one pure function signature and one `__main__` wiring.

**Observed state (2026-06-20).** Both `hello.py` and `test_hello.py` already match the target design (see Appendix A). Implementation work for this request reduces to *verification* (and optional minor hardening that does not alter the contract). The TDD documents the contract that downstream phases must continue to honor.

### 1.1 Key Design Decisions

1. **Pure function, single module.** `greet` lives at module top level of `hello.py`. No package, no `src/` layout, no class. — Drives FR-1 with minimal architectural footprint.
2. **F-string for body.** `return f"hello {name}"` keeps implementation trivially correct and traceable to FR-3.
3. **`__main__` calls `print(greet())`.** No `argparse`, no `sys.argv` parsing, no envvars — preserves the exact CLI contract (FR-5) and the Non-Goals in PRD §2.2.
4. **Tests at repo root, importing directly.** `test_hello.py` sits next to `hello.py`; tests `import` `greet` directly (no subprocess for unit tests) and use `sys.executable` for the CLI subprocess test (NFR-2, technical constraint §7).
5. **No new dependencies.** Standard library only at runtime; pytest at dev time, which already exists per `.pytest_cache/`.

## 3. Detailed Design

### 3.1 `hello.py`

The module contains exactly two top-level items:

1. The function `greet`.
2. The `if __name__ == "__main__":` guard that prints the default greeting.

**Pseudocode** (illustrative — see Appendix A for current implementation):

```
def greet(name: str = "world") -> str:
    return "hello " + name   # or equivalent f-string

if __name__ == "__main__":
    print(greet())
```

**Invariants.**

- `greet` is pure: no globals read or written, no I/O, no clock, no randomness (NFR-4).
- `greet` is O(1) in time and space (NFR-1) — string formatting of a short literal plus the argument.
- `greet` performs no validation of `name`; the parameter type annotation is documentary (Python does not enforce it) and matches the PRD's explicit Non-Goal of input validation (PRD §2.2).
- The module imports nothing — the implementation must remain dependency-free at module scope.
- LOC budget: ≤ 10 non-blank lines (PRD §8).

### 3.2 `test_hello.py`

Three pytest test functions, all module-level, all synchronous:

1. `test_greet_default_returns_hello_world` — asserts `greet() == "hello world"`. Traces FR-2, FR-7.
2. `test_greet_with_custom_name_returns_hello_name` — asserts `greet("ada") == "hello ada"`. Traces FR-3, FR-8.
3. `test_hello_prints_hello_world` — runs `subprocess.run([sys.executable, str(SCRIPT)], capture_output=True, text=True, timeout=5)`; asserts `returncode == 0`, `stdout.strip() == "hello world"`, `stderr == ""`. Traces FR-5, FR-9.

**Test-design conventions.**

- Use `sys.executable` (not a hard-coded `"python"`) for the CLI subprocess (technical constraint §7, NFR-2).
- Resolve the script path with `Path(__file__).parent / "hello.py"` so the test is location-independent.
- 5-second timeout on the subprocess (NFR-1).
- Tests import `greet` directly from `hello` — they MUST NOT shell out for the unit-test cases.
- No fixtures, no parametrization required for the in-scope cases. (A future PRD may parametrize; out of scope here.)

## 4. API Specification

Public surface of the `hello` module (additions to consider exhaustively listed):

| Name | Kind | Signature | Description |
| --- | --- | --- | --- |
| `greet` | function | `greet(name: str = "world") -> str` | Returns the literal `"hello "` concatenated with `name`. Pure, no side effects. |

**Usage examples.**

```python
from hello import greet

greet()             # → "hello world"
greet("ada")        # → "hello ada"
greet(name="ada")   # → "hello ada"  (kwarg form also supported)
```

**Inputs.** `name`: any `str`. No validation, no normalization, no escaping. Behavior with non-`str` inputs is undefined and out of scope (PRD §2.2).

**Outputs.** A new `str` of the form `f"hello {name}"`. The function never raises for any `str` input.

**Backward compatibility.** This is purely additive at the module level — there was no prior `greet` symbol — and the `__main__` CLI output is bit-for-bit unchanged. No deprecations, no migration.

**Coverage mapping to PRD acceptance checklist** (PRD §11):

- `hello.py` defines `greet(...) -> str` → asserted by `test_greet_default_returns_hello_world` + import.
- `__main__` block calls `print(greet())` → exercised by `test_hello_prints_hello_world`.
- CLI prints `hello world\n`, exit 0, empty stderr → `test_hello_prints_hello_world`.
- Default + custom-name tests present → unit tests 1 & 2.
- No new runtime deps → reviewer / executor verifies `hello.py` has no `import` statements (or only stdlib imports if any are added).

## 8. Security Considerations

**N/A — no new surface.** No untrusted input (the default call site is the developer-controlled `__main__`); no I/O beyond writing to stdout; no eval/exec; no secrets; no network; no filesystem writes. The subprocess test launches a known-path script with no shell interpolation (`shell=False` is the default for `subprocess.run` with a list argv) and uses `sys.executable`, so there is no PATH-hijacking surface.

## 9. Performance Considerations

`greet` is O(1) and allocates one short string. The full pytest suite is dominated by a single ~tens-of-milliseconds Python interpreter spawn for the subprocess test, well under the 5-second NFR-1 budget. No caching, batching, async, or pooling is warranted.

## 10. Architecture Decision Records

### ADR-001: Keep the script as a single top-level file (no `src/` layout, no package)

- **Context.** PRD §7 / Non-Goals §2.2 prohibit packaging into a wheel or introducing new file layout.
- **Options considered.**
  1. Keep `hello.py` and `test_hello.py` at repo root. *(chosen)*
  2. Move to a `src/hello/` package with `__init__.py` re-exporting `greet`.
  3. Convert to an installable wheel with a console-script entry point.
- **Decision.** Option 1.
- **Rationale.** Smallest possible diff that satisfies FR-1..FR-10. Options 2 and 3 explicitly violate PRD Non-Goals.
- **Consequences.** Tests rely on the repo root being on `sys.path` (pytest's default rootdir discovery handles this). If a future request adds a real package, this TDD will need to be superseded.
- **Traces to.** PRD §7, §2.2.

### ADR-002: Implement the body with an f-string

- **Context.** FR-3 specifies the return value as `f"hello {name}"`.
- **Options considered.**
  1. `return f"hello {name}"` *(chosen)*
  2. `return "hello " + name`
  3. `return "hello %s" % name` / `"hello {}".format(name)`
- **Decision.** Option 1.
- **Rationale.** Matches PRD wording verbatim, is the idiomatic modern Python style, requires Python ≥ 3.6 which is universally available.
- **Consequences.** Drops support for Python < 3.6 — acceptable per PRD §7.
- **Traces to.** FR-3, PRD §7.

### ADR-003: Subprocess test uses `sys.executable`, not the literal `"python"`

- **Context.** Tests must work regardless of which Python interpreter pytest is invoked from, including virtualenvs where `python` may not exist on PATH.
- **Options considered.**
  1. `subprocess.run([sys.executable, str(SCRIPT)], ...)` *(chosen)*
  2. `subprocess.run(["python", str(SCRIPT)], ...)`
  3. `subprocess.run(["python3", str(SCRIPT)], ...)`
- **Decision.** Option 1.
- **Rationale.** Portability and venv-correctness; explicitly required by PRD §7.
- **Consequences.** None negative.
- **Traces to.** PRD §7, NFR-2.

### ADR-004: No input validation, type-coercion, or error handling in `greet`

- **Context.** PRD §2.2 lists "Input validation, sanitization, or type coercion" as Non-Goals.
- **Options considered.**
  1. No validation. *(chosen)*
  2. `if not isinstance(name, str): raise TypeError(...)`.
- **Decision.** Option 1.
- **Rationale.** Matches PRD scope; keeps the function trivially correct and avoids inventing an error taxonomy this request doesn't need.
- **Consequences.** Calling `greet(123)` would yield `"hello 123"` (Python's f-string `__format__` semantics). This is acceptable because the documented contract is `str → str`.
- **Traces to.** PRD §2.2, NFR-3.

```python
import subprocess
import sys
from pathlib import Path

from hello import greet

SCRIPT = Path(__file__).parent / "hello.py"

        text=True,
        timeout=5,

    assert result.stdout.strip() == "hello world"
    assert result.stderr == ""


def test_greet_default_returns_hello_world() -> None:
    assert greet() == "hello world"


def test_greet_with_custom_name_returns_hello_name() -> None:
    assert greet("ada") == "hello ada"
```
