## 1. Problem Statement

The `smoke-hello` repository currently contains a minimal `hello.py` script whose
behavior is to print `hello world` to standard output. Because the greeting
logic is inlined inside the `__main__` block, it cannot be reused
programmatically — there is no importable function to call from other modules
or from unit tests, and the message is not parameterizable by name.

This limits:

1. **Testability** — only an end-to-end subprocess test of script output is
   possible; isolated unit tests of greeting logic require a function-level API.
2. **Reusability** — downstream code cannot import a greeting helper.
3. **Extensibility** — adding new greeting targets (e.g., `greet('ada')`)
   requires editing the script rather than calling an API.

A small refactor that extracts a `greet(name='world')` function eliminates all
three limitations without changing user-observable script behavior.

## 2. Goals and Non-Goals

### 2.1 Goals

- **G1**: Provide an importable, pure function `greet(name: str = 'world') -> str`
  in `hello.py` that returns `'hello <name>'`.
- **G2**: Preserve the existing CLI behavior — `python hello.py` must print
  exactly `hello world\n` to stdout with exit code 0 and no stderr output.
- **G3**: Add pytest unit tests in `test_hello.py` that exercise `greet()` with
  both the default argument and a custom name.
- **G4**: Keep the existing script-output test (subprocess invocation of
  `hello.py`) passing without modification of its assertions.

### 2.2 Non-Goals

- **NG1**: Adding command-line argument parsing (e.g., `argparse`) to let a
  user pass a name from the shell. Out of scope.
- **NG2**: Internationalization or localization of the greeting string.
- **NG3**: Packaging `hello` as a distributable Python package (no `setup.py`,
  `pyproject.toml`, or `__init__.py` introduction is required).
- **NG4**: Logging, configuration, or any I/O beyond the existing `print()`.
- **NG5**: Type-checking infrastructure (mypy config, CI, etc.) beyond the
  inline type hints on `greet`.

## 4. User Stories

### Epic E1: Reusable greeting API

**US-1 (Priority: P0)** — As a Python developer importing from `hello.py`, I
want to call `greet()` with no arguments so that I receive the canonical
`'hello world'` string without spawning a subprocess.

- **Given** `hello.py` is on the Python path
- **When** I execute `from hello import greet; result = greet()`
- **Then** `result` equals the string `'hello world'`

**US-2 (Priority: P0)** — As a Python developer, I want to pass a custom name
to `greet()` so that I receive a personalized greeting string.

- **Given** `hello.py` is on the Python path
- **When** I execute `from hello import greet; result = greet('ada')`
- **Then** `result` equals the string `'hello ada'`

### Epic E2: Backward-compatible CLI behavior

**US-3 (Priority: P0)** — As an existing user of the `hello.py` script, I want
`python hello.py` to continue printing `hello world` so that no consumer
relying on script output is broken.

- **Given** the refactored `hello.py`
- **When** I run `python hello.py`
- **Then** stdout (trimmed of trailing whitespace) equals `'hello world'`,
  stderr is empty, and the exit code is `0`

### Epic E3: Test coverage

**US-4 (Priority: P0)** — As a maintainer, I want unit tests for `greet()` in
`test_hello.py` so that regressions in greeting logic are caught without
relying on subprocess execution.

- **Given** the test suite
- **When** I run `pytest` from the repo root
- **Then** at least one test asserts `greet() == 'hello world'`, at least one
  test asserts `greet('ada') == 'hello ada'`, and the pre-existing
  script-output test continues to pass
