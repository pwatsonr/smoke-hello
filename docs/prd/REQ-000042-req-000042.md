## Problem Statement
`hello.py` historically existed as a single-line script (`print("hello world")`) with no reusable function. The original `test_hello.py` only verified script stdout via a subprocess invocation; there were no unit tests against any callable API. This limited reusability of the greeting logic and prevented standard, fast-running unit tests.

This request refactors `hello.py` to expose a pure, callable `greet(name='world')` function that returns the greeting string, while the `__main__` block continues to print the same output. New pytest unit tests must cover both the default argument and a custom name. The existing subprocess-based script-output test must continue to pass unchanged so external behavior is preserved.

Note: A prior request (REQ-000024) introduced an equivalent refactor. REQ-000042 re-specifies the contract independently so it can be validated end-to-end by the autonomous-dev pipeline regardless of whether the source is already in the desired shape. The PRD's acceptance criteria must hold against whatever state the repository is in at code-phase exit.

## Goals
- **G1**: Define a function `greet(name='world')` in `hello.py` that returns the string `"hello <name>"`.
- **G2**: Update (or preserve) the `__main__` entry point of `hello.py` to print the value returned by `greet()` so that `python hello.py` still prints exactly `hello world` to stdout.
- **G3**: Ensure pytest unit tests in `test_hello.py` cover at minimum (a) the default behavior `greet() == "hello world"` and (b) a custom name `greet("ada") == "hello ada"`.
- **G4**: Preserve the existing subprocess-based script-output test so it continues to pass without weakening its assertions.

## Non-Goals
- **NG1**: No CLI argument parsing (no `argparse`, no `sys.argv` handling) for the name.
- **NG2**: No internationalization, capitalization rules, punctuation, or trailing exclamation.
- **NG3**: No packaging changes (no `pyproject.toml`, no `setup.py`, no `__init__.py`).
- **NG4**: No type stubs, no `mypy` configuration, no linter configuration changes.
- **NG5**: No new dependencies beyond `pytest` (assumed already available in the test environment).
- **NG6**: No changes to `README.md` or any other repository file outside `hello.py` and `test_hello.py`.
- **NG7**: No environment variable handling, no logging framework integration.

## User Stories

### US-1 (Priority: P0) — Reusable greet function
**As a** developer consuming `hello.py`,
**I want** a `greet(name='world')` function that returns the greeting string,
**so that** I can call it programmatically without invoking a subprocess.

**Acceptance Criteria**
- **Given** `hello.py` exposes `greet`,
- **When** I `from hello import greet` and call `greet()`,
- **Then** the return value MUST equal exactly the string `"hello world"`.
- **And When** I call `greet("ada")`,
- **Then** the return value MUST equal exactly the string `"hello ada"`.

### US-2 (Priority: P0) — Preserve CLI behavior
**As an** autonomous-dev maintainer,
**I want** `python hello.py` to continue printing exactly `hello world`,
**so that** the existing subprocess-based test and any external smoke checks continue to pass.

**Acceptance Criteria**
- **Given** the refactored `hello.py`,
- **When** I run `python hello.py`,
- **Then** stdout MUST be exactly `hello world\n` (single line, single trailing newline) and stderr MUST be empty and exit code MUST be `0`.

### US-3 (Priority: P0) — Unit test coverage for greet
**As an** autonomous-dev reviewer,
**I want** pytest unit tests that directly call `greet()`,
**so that** the function's contract is verified without spawning a subprocess.

**Acceptance Criteria**
- **Given** `test_hello.py`,
- **When** I run `pytest test_hello.py`,
- **Then** at least one test verifies `greet() == "hello world"`,
- **And** at least one test verifies `greet("ada") == "hello ada"` (or an equivalent non-default name),
- **And** the existing test `test_hello_prints_hello_world` continues to pass with its original assertions intact.

### US-4 (Priority: P1) — No import-time side effects
**As a** test author importing `hello`,
**I want** `import hello` to not print to stdout,
**so that** unit tests can import and call `greet` without polluting test output.

**Acceptance Criteria**
- **Given** the refactored `hello.py`,
- **When** the module is imported (`import hello`),
- **Then** nothing MUST be printed to stdout or stderr during import. The `print(greet())` call MUST be guarded by `if __name__ == "__main__":`.

## Functional Requirements

### Source: `hello.py`
- **FR-1**: `hello.py` MUST define a top-level function with the exact signature `greet(name='world')` (default value is the lowercase literal `"world"`).
- **FR-2**: `greet(name)` MUST return the string produced by concatenating the literal `"hello "` (one space) with `name` (equivalent to `f"hello {name}"`). The return type MUST be `str`.
- **FR-3**: `greet()` (no arguments) MUST return exactly the string `"hello world"`.
- **FR-4**: `greet("ada")` MUST return exactly the string `"hello ada"`.
- **FR-5**: `hello.py` MUST contain an `if __name__ == "__main__":` block that calls `print(greet())`.
- **FR-6**: Importing `hello` (`import hello`) MUST NOT produce any stdout or stderr output and MUST NOT raise.
- **FR-7**: Running `python hello.py` MUST print exactly `hello world` followed by a single newline to stdout, with empty stderr and exit code `0`.
- **FR-8**: `hello.py` MUST NOT introduce any non-standard-library imports.

### Tests: `test_hello.py`
- **FR-9**: `test_hello.py` MUST contain a test function `test_hello_prints_hello_world` that invokes `hello.py` as a subprocess and asserts `returncode == 0`, `stdout.strip() == "hello world"`, and `stderr == ""`.
- **FR-10**: `test_hello.py` MUST contain at least one unit test that imports `greet` from `hello` and asserts `greet() == "hello world"`.
- **FR-11**: `test_hello.py` MUST contain at least one unit test that asserts `greet("ada") == "hello ada"` (or an equivalent custom-name case using a non-default argument).
- **FR-12**: All tests MUST be discoverable by `pytest` using default discovery rules (test function names prefixed with `test_`).
- **FR-13**: No new test fixtures, plugins, or `conftest.py` files are required; tests MUST be self-contained and rely only on the standard library plus `pytest`.

### Acceptance Tests (verifiable)
- **AT-1**: `python -c "from hello import greet; assert greet() == 'hello world'"` exits with status `0`.
- **AT-2**: `python -c "from hello import greet; assert greet('ada') == 'hello ada'"` exits with status `0`.
- **AT-3**: `python hello.py` produces stdout exactly equal to `hello world\n`, stderr empty, exit code `0`.
- **AT-4**: `python -c "import hello"` produces empty stdout and empty stderr.
- **AT-5**: `pytest test_hello.py` reports all tests passing, including `test_hello_prints_hello_world` and the new `greet` unit tests.
- **AT-6**: `pytest test_hello.py -k greet` matches at least two tests (default + custom name) and all selected tests pass.
- **AT-7**: `git status --porcelain` after the change lists at most `M hello.py` and `M test_hello.py` (no other files modified, added, renamed, or deleted) — except for autonomous-dev artifacts under `.autonomous-dev/` and `docs/`.

## Non-Functional Requirements
- **NFR-1 (Purity)**: `greet` MUST be a pure function: no I/O, no global state mutation, no randomness, no time dependence.
- **NFR-2 (Performance)**: `greet` MUST return in O(1) time relative to typical name lengths; total wall-clock execution of `pytest test_hello.py` MUST remain under 5 seconds on a developer laptop.
- **NFR-3 (Readability)**: Source MUST remain plain ASCII/UTF-8, idiomatic Python (PEP 8 spacing), and fit on a screen without scrolling (≤ 15 lines in `hello.py`).
- **NFR-4 (Compatibility)**: Code MUST be compatible with Python 3.9+ (no syntax requiring newer versions; f-strings are acceptable).
- **NFR-5 (Backward Compatibility)**: External CLI behavior of `python hello.py` MUST be byte-for-byte identical to the pre-change behavior.
- **NFR-6 (Testability)**: Unit tests MUST execute without network access, without writing files, and without subprocess for the new `greet` tests (the existing subprocess test is retained).
- **NFR-7 (Atomicity)**: The source change MUST be scoped to exactly `hello.py` and `test_hello.py`.

## Risks
- **R-1 (Low) — Output drift**: An implementer might inadvertently change the printed string (e.g., add punctuation). *Mitigation*: FR-3, FR-7, AT-3 explicitly pin the exact string.
- **R-2 (Low) — Import-time side effects**: Forgetting the `if __name__ == "__main__":` guard would cause `import hello` to print, breaking US-4. *Mitigation*: FR-5, FR-6, AT-4 explicitly require the guard and silent import.
- **R-3 (Low) — Existing test regression**: Weakening or removing `test_hello_prints_hello_world` would violate G4. *Mitigation*: FR-9 pins its assertions.
- **R-4 (Low) — Discovery path**: If pytest is invoked from a non-root directory, `from hello import greet` could fail. *Mitigation*: TC-4 documents the expected invocation directory; the pipeline runs pytest from repo root.
- **R-5 (Low) — Signature drift**: Using a different default (e.g., `name="World"`) would violate FR-1 and FR-3. *Mitigation*: FR-1 pins the exact signature `greet(name='world')` (lowercase `world`).
- **R-6 (Low) — Idempotency on already-satisfied repo state**: Because TC-2 documents that the contract may already hold, the implementer must not introduce gratuitous changes purely to produce a diff. *Mitigation*: NFR-7 plus the requirement that all FRs hold; if the contract already holds, a no-op code phase is acceptable.

## Open Questions
- **OQ-1**: Should the unit tests use `pytest.mark.parametrize` to cover both the default and custom name in a single parametric test, or two separate test functions? *Recommendation*: either is acceptable; FR-10 and FR-11 only require that both cases are asserted.
- **OQ-2**: Should an additional edge-case test be added (e.g., empty string `greet("") == "hello "`)? *Recommendation*: optional; not required by FR-10/FR-11. If added, it MUST match the literal concatenation contract in FR-2.
- **OQ-3**: Should `greet` carry a type annotation (`def greet(name: str = "world") -> str:`)? *Recommendation*: optional; not required by FR-1 (which pins the signature shape but does not mandate annotations). Adding annotations is permitted and does not violate any FR.
- **OQ-4**: If the repo state already satisfies all FRs (as documented in TC-2), should the code phase still produce a commit? *Recommendation*: a no-op or minimal-touch commit is acceptable so long as all acceptance tests pass.

import subprocess
import sys
from pathlib import Path

from hello import greet

SCRIPT = Path(__file__).parent / "hello.py"


def test_hello_prints_hello_world() -> None:
    result = subprocess.run(
        [sys.executable, str(SCRIPT)],
        capture_output=True,
        text=True,
        timeout=5,
    )
    assert result.returncode == 0
    assert result.stdout.strip() == "hello world"
    assert result.stderr == ""


def test_greet_default_returns_hello_world() -> None:
    assert greet() == "hello world"


def test_greet_with_custom_name_returns_hello_name() -> None:
    assert greet("ada") == "hello ada"
