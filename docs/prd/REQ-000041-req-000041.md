## 1. Problem Statement

The `smoke-hello` repository contains a minimal Python script, `hello.py`, that prints `hello world` when executed. In its earliest form the greeting logic was inline in the `__main__` block, which made it impossible to import the greeting behavior from other Python modules (such as test suites or downstream consumers) without invoking a subprocess. This limited:

- **Unit testability**: The only way to verify behavior was to launch a subprocess and capture stdout — slow, brittle, and unable to test alternative inputs.
- **Reusability**: Other modules could not call the greeting logic directly with custom names.

This request formalizes a refactor that extracts the greeting into a `greet(name='world')` function and adds direct unit tests for it, while preserving the script's existing CLI behavior so that no external caller breaks.

> Note: Inspection of the repository on 2026-06-20 shows that the source (`hello.py`) and tests (`test_hello.py`) already match the desired end state described below. This PRD therefore documents the requirements that the implementation must continue to satisfy after the refactor (and that the executor / reviewer phases should verify).

## 2. Goals and Non-Goals

### 2.1 Goals (In Scope)

1. Provide a callable Python function `greet(name: str = "world") -> str` in `hello.py` that returns the string `"hello <name>"`.
2. Preserve the existing CLI contract: `python hello.py` must print exactly `hello world\n` (one line, no extra whitespace, no stderr output, exit code 0).
3. Provide pytest-based unit tests in `test_hello.py` that:
   - Verify `greet()` returns `"hello world"` (default-argument case).
   - Verify `greet("ada")` returns `"hello ada"` (custom-name case).
   - Continue to verify the script-output behavior (subprocess test).
4. Ensure all tests pass under `pytest` with the project's existing tooling configuration.

### 2.2 Non-Goals (Out of Scope)

- Adding command-line argument parsing (e.g., `argparse`) so the user can pass a name on the CLI.
- Internationalization / localization of the greeting.
- Input validation, sanitization, or type coercion beyond the existing `str` type hint.
- Packaging the script as an installable module / wheel.
- Adding logging, configuration, or environment-variable support.
- Changing the output language, casing, or punctuation of the greeting.

## 4. User Stories

### Epic E1 — Importable Greeting

**US-1 (P0)**: As a Python developer importing `hello`, I want to call `greet()` directly so that I can use the greeting logic without spawning a subprocess.

- **Given** the module `hello` is importable on the Python path
- **When** I execute `from hello import greet; greet()`
- **Then** the returned value is exactly the string `"hello world"`.

**US-2 (P0)**: As a Python developer, I want to pass a custom name to `greet()` so that I can produce personalized greetings.

- **Given** the function `greet` from `hello` is imported
- **When** I call `greet("ada")`
- **Then** the returned value is exactly the string `"hello ada"`.

### Epic E2 — Preserved CLI Behavior

**US-3 (P0)**: As an existing user who runs `python hello.py`, I want the script to keep printing `hello world` so that no existing automation breaks.

- **Given** the file `hello.py` exists in the working directory
- **When** I run `python hello.py`
- **Then** the process exits with code `0`, stdout (stripped) equals `"hello world"`, and stderr is empty.

### Epic E3 — Test Coverage

**US-4 (P0)**: As a maintainer, I want pytest unit tests that exercise both `greet()` invocations and the CLI behavior so that regressions are caught automatically.

- **Given** the test file `test_hello.py`
- **When** I run `pytest`
- **Then** at minimum three tests exist and all pass: (a) default `greet()`, (b) custom-name `greet("ada")`, (c) subprocess CLI test of `python hello.py`.

## 6. Non-Functional Requirements

| ID | Category | Requirement |
| --- | --- | --- |
| NFR-1 | Performance | A single `greet()` invocation SHALL complete in O(1) time and use no I/O. Full pytest suite SHALL complete in under 5 seconds on a developer laptop (subprocess test uses a 5-second timeout — see FR-9). |
| NFR-2 | Compatibility | The module SHALL run on the system Python interpreter resolved by `sys.executable`. No third-party runtime dependency beyond the Python standard library SHALL be introduced (pytest is a dev-time test dependency only). |
| NFR-3 | Style / Types | `greet` SHALL include PEP 484 type annotations on parameters and return value. Code SHALL conform to PEP 8 (formatting handled by the repository's default tooling). |
| NFR-4 | Determinism | `greet` SHALL be a pure function: no side effects, no global state, no randomness, no time-dependence. |
| NFR-5 | Backward Compatibility | The CLI contract (FR-5) SHALL NOT change. No new required CLI arguments SHALL be introduced. |
| NFR-6 | Testability | Tests SHALL NOT depend on network, filesystem state beyond the repository, or environment variables. |
| NFR-7 | Encoding | Output SHALL be ASCII (no BOM, no trailing whitespace other than the single terminal newline emitted by `print`). |

## 7. Technical Constraints

- **Language**: Python 3 (the version installed at `sys.executable`); no specific minimum version is mandated by the request, but f-string usage (PEP 498) requires ≥ 3.6.
- **File layout**: `hello.py` and `test_hello.py` live at the repository root; no package directory is introduced.
- **Test framework**: `pytest` (consistent with the existing `.pytest_cache/` already present in the repository).
- **No external dependencies**: Standard library only for `hello.py`; standard library + pytest for tests.
- **Subprocess invocation**: Tests SHALL use `sys.executable` (not a hard-coded `"python"`) to launch the script for portability.

## 9. Risks and Mitigations

| Risk | Severity | Mitigation |
| --- | --- | --- |
| Trailing newline / whitespace mismatch in CLI test | Low | Test uses `stdout.strip()` and asserts equality; documented in FR-5 and FR-9. |
| Custom name containing special characters could change output | Low | Out of scope (no input validation); test covers a representative alphabetic name (`"ada"`). |
